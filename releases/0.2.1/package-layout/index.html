    Package layout and transferring feature work

    The application is one installable Python package. Subpackages organize existing responsibilities; they do not define separate services, distributions or plugins. Use explicit imports from implementation modules. Package initializers do not load feature implementations, register providers or start background services.

    Ownership

    Package Responsibility
    portfolio Holdings, positions, valuation, allocation, targets and rebalancing
    exposure Normalized exposures, taxonomy, aggregation and classifications
    funds / funds.providers ETF snapshots, expansion, discovery, refresh and isolated provider parsing
    ledger Account/security facts, replay, corrections and recoverable publication
    performance Cost basis, gains, historical evidence, coverage, TWR and IRR
    analytics Fundamentals, concentration, risk and associated service/cache ownership
    derivatives Actual contracts, observations, margin, settlements and valuation
    studies Hypothetical scenarios, historical reconstruction and the legacy futures sandbox
    market Prices, FX, market-price history, listing lookup and request coordination
    ingestion CSV/PDF readers, normalization, matching and import reconstruction
    taxes Investment-fund tax estimates, acquisition-month projection and tax-specific evidence
    monitoring Rules, observations, scheduling, presentation models and alert persistence
    workspace Shared storage mechanics, locking, backups, selection and activation
    runtime Launch, server/desktop lifetime, documentation serving and OS integration
    demo_data Explicitly synthetic portfolio and history builders
    interface.shared Reusable controls, charts, formatting, notifications and session state
    interface.views Feature views, grouped by the domain presented

    application.py remains the portfolio preparation/composition boundary. settings.py owns shared identity, settings and package resource paths. privacy.py remains independently executable by the Git hook. Resources remain in assets/ and intro_frontend/ at the package root.

    Market-price history is distinct from account/security replay and portfolio performance history. Actual derivative wealth remains separate from hypothetical study results. Shared file-writing mechanics belong to workspace; feature-specific persistence and publication stay with their feature. Pure exposure and performance presentation transformations stay beside their calculations. Moving modules does not move calculations into Streamlit or change the documented financial pipeline.

    The directory name ingestion intentionally avoids imports, which the privacy checker reserves for private data. Keep that protection enabled.

    Supported entrypoints

    The installed commands portfolio-app, portfolio-window, portfolio-desktop and portfolio-check-private retain their names and arguments. Root modules app, window, gui, ui, intro_preview, demo_history, etf_sources and vaneck retain executable adapters for existing commands and script paths. portfolio_app.ui.render_app also remains available.

    Internal code and test patches must use the canonical implementation paths below. Adapters are not copies of their implementations and do not alias old modules in sys.modules. Patching an adapter's exported function does not patch globals used inside the implementation. For example, patch portfolio_app.runtime.app.run_server, not portfolio_app.app.run_server.

    Use settings.package_path(...) for resources or executable scripts rooted in the package; a moved module's __file__ no longer identifies that root. Preserve function-local imports that defer expensive work or break dependency cycles.

    Transferring active work from the flat layout

    This procedure supports active feature work based on the pre-migration main. It does not require reconstructing historical branches or changing another session's worktree. Identify the feature owner and source state first; a dirty or divergent worktree alone does not establish that its work is active or belongs to the current task.

    1. Record the original feature branch, commit, common base and source changes in external working notes. Review which changes belong to the feature.
    2. Create a separate integration branch/worktree from the feature tip. Keep the original branch/worktree intact. For committed work, a typical sequence is:

    sh git worktree add -b integrate/my-feature ../my-feature-integration feature/my-feature cd ../my-feature-integration git merge --no-commit --no-ff main

    Here main must already contain the complete package migration. A pending migration branch may instead be used for a rehearsal; record its exact commit. Merge both histories. Do not cherry-pick the migration onto a stale base.

    1. If the source has uncommitted feature work, copy and verify the deliberately selected tracked edits and required new source files into the integration worktree before merging. Preserve file additions, deletions and executable bits. Review and checkpoint that work there with the normal privacy checks. Do not copy private data, local configuration or unrelated changes. Do not stash, reset or clean the source worktree.
    2. Let Git apply recognized rename/edit combinations. Inspect git diff --name-status --find-renames and git status. Resolve unrecognized moves using the table below; retain one canonical implementation. Do not resurrect the old file to silence an import error. Handle retained adapters explicitly: the eight adapter paths still exist, so Git may treat their old implementations as edits to those adapters rather than as moves. If the feature touched one of them, compare its original diff against the common base and port its implementation changes to the canonical destination. Then restore the thin adapter from migrated main in the integration worktree. Verify both files even if Git reported a clean merge; feature code must not accidentally remain in an adapter.
    3. Reconcile new imports, package-member imports, mock/monkeypatch strings, generated Streamlit code, subprocess arguments and resource/script paths. New files have no rename history: place them according to the ownership table and update their callers. A genuine overlapping edit requires reviewing both changes, even when Git resolves the path automatically.
    4. Inspect the combined diff against migrated main. Run affected feature tests, then the required integration checks from the development and release guides. Use the integration worktree's own uv environment, an independent preview port and generated synthetic data. Check staged privacy and contents before the integration commit. Do not retire the original worktree until the owner has confirmed the transferred result.

    Common adjustments

    An edit to holdings.py belongs in portfolio/holdings.py; its import becomes:

    from portfolio_app.portfolio.holdings import DataError

    A feature adding a new market provider places it under market/ and updates its callers even though Git has no old file to match. A generated Streamlit script must use the same canonical imports as ordinary source. The stable root ui.py script can still be used by existing launch commands.

    An existing test patch such as portfolio_app.prices.PriceService becomes portfolio_app.market.prices.PriceService. Continue patching the name where the consumer looks it up; if a consumer imported the class into its own module, patch that consumer's new module path instead.

    If both histories alter the same import or function, combine the feature behavior with the new canonical path. Never select one complete side merely to clear the conflict. Use the existing feature tests to establish that its behavior survived.
